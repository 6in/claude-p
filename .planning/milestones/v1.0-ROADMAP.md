# Roadmap: ht-webif

**Milestone:** v1 — "webif/ を本格的な開発リポジトリとして整える"
**Created:** 2026-05-23
**Granularity:** coarse (target 3-5 phases)
**Coverage:** 11/11 v1 requirements mapped

## Overview

ht-webif の v1 マイルストーンは、既に動いているプロトタイプ（PROJECT.md の Validated にある WEBIF-01..13）を「他人が触れる開発リポジトリ」へ昇格させる作業を扱う。アプリ機能の追加ではなく、リポジトリ体裁・コード構造・テスト基盤・CI 自動化という土台側の整備に集中する。3 フェーズで段階的に進める: まずリスクの低いリポジトリ体裁（README/LICENSE/.gitignore/Cargo.toml）を整え、次に挙動を変えずに単一ファイル main.rs をモジュール分割し、最後にテストと CI を載せる。フェーズ間の依存は単方向: 体裁 → 構造 → テスト/CI。

## Phase Details

### Phase 1: Repository Hygiene

**Goal**: 初見の開発者が `webif/` の正体・ビルド方法・ライセンス条件・無視ルールを README と LICENSE と .gitignore と Cargo.toml だけ見て把握できる状態にする
**Depends on**: Nothing (first phase)
**Requirements**: REPO-01, REPO-02, REPO-03, REPO-04
**Success Criteria** (what must be TRUE):

  1. リポジトリの README.md を開くと、プロジェクト概要・前提依存（ht-mcp / claude CLI）・ビルド手順・起動手順・4 つの HTTP エンドポイントの API 例が確認できる
  2. リポジトリ直下に LICENSE ファイル（MIT または Apache-2.0）が存在し、`webif/Cargo.toml` の `license` フィールドと一致する
  3. `.gitignore` が `target/`、`turns/`、`.env`、IDE/OS 生成物（`.idea/`、`.vscode/`、`.DS_Store` 等）を除外しており、`git status` のクリーン時にビルド成果物・ランタイム成果物・秘密情報がトラックされていない
  4. `webif/Cargo.toml` に `description`、`repository`、`license`、`authors`、`readme`、`edition` のメタデータが揃い、`cargo metadata` で取得できる

**Plans:** 3/3 plans complete
Plans:

- [x] 01-01-PLAN.md — `.gitignore` 整備（target/、turns/、.env、IDE/OS）+ webif/.gitignore 統合（REPO-03）
- [x] 01-02-PLAN.md — LICENSE（MIT 全文）追加 + webif/Cargo.toml メタデータ拡張（description/repository/license/authors/readme/edition）（REPO-02、REPO-04）
- [x] 01-03-PLAN.md — README.md を新規作成（プロジェクト概要・前提・ビルド/起動・4 エンドポイント curl 例・ライセンス）（REPO-01）

### Phase 2: Module Refactor

**Goal**: 単一ファイル `webif/src/main.rs`（~561 行）を責務ごとのモジュールへ分割し、`main.rs` は配線のみの薄い起点に縮める。HTTP API の挙動は完全に保つ
**Depends on**: Phase 1
**Requirements**: CODE-01, CODE-02
**Success Criteria** (what must be TRUE):

  1. `webif/src/` 配下に `mcp_client`、`worker`、`turn`、`handlers`、`config` 相当のモジュール（または `lib.rs` 配下のサブモジュール）が存在し、`main.rs` は wiring（環境変数読込・ルータ構築・サーバ起動）のみになっている
  2. `cargo build --release` が警告なく完了し、`cargo run` で起動した WebIF が `POST /prompt`・`GET /turns/{id}`・`POST /command`・`POST /restart` の 4 エンドポイントを既存と同一の挙動で応答する（同期/非同期、`fresh:true`、`wait:true` を含む）
  3. 既存の HT-PROTOCOL v1.1 ターンファイル方式（`prompt-/result-/status-<turnId>`）が分割後も同じファイル名・同じディレクトリ（`turns/`）で動作する
  4. モジュール境界が明示的になり、`McpClient`（stdio JSON-RPC）、`Worker`（claude セッション寿命）、ターン処理（`Job`/`process_job`/`worker_loop`）、HTTP ハンドラ、設定読込が個別ファイルに分かれている

**Plans:** 4 plans

### Phase 3: Testing & CI Automation

**Goal**: モジュール分割後のコードに最小限のテストを載せ、`justfile` と GitHub Actions で `fmt`・`clippy`・`test` を自動化する。以後の変更で回帰が検知できる状態を作る
**Depends on**: Phase 2
**Requirements**: TEST-01, TEST-02, TEST-03, TOOL-01, TOOL-02
**Success Criteria** (what must be TRUE):

  1. `cargo test` を実行すると、純粋関数（turn_id 生成・パス組み立て・prompt body 組み立て等）の単体テストと、MCP クライアントの JSON-RPC リクエスト/レスポンス組み立てテストが green で通る
  2. HTTP ハンドラの統合テスト（ht-mcp をモック/スタブ化）が `cargo test` で実行され、`/turns/{id}` のパストラバーサル拒否（`../` や不正文字を 400 で弾く）と happy path（status ファイル出現で完了レスポンスが返る）の両方を検証している
  3. リポジトリ直下に `justfile` または `Makefile` が存在し、`just build` / `just run` / `just test` / `just fmt` / `just clippy` / `just clean` の各サブコマンドが期待通りの cargo コマンドへ展開される
  4. `.github/workflows/ci.yml` が push と PR をトリガに `cargo fmt --check`・`cargo clippy -- -D warnings`・`cargo test` を実行し、いずれかが失敗すると CI が赤くなる

**Plans:** 4/6 plans executed
