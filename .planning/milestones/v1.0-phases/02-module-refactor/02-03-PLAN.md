<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `Arc<Mutex<Worker>>` 共有境界 | worker_loop と HTTP ハンドラ（command/restart）が同一の Mutex<Worker> を排他共有する。共有が壊れると claude セッション状態が分岐する |
| `tokio::sync::Mutex` vs `std::sync::Mutex` | `.await` 越しに guard を保持するため tokio 版必須。std 版に置換するとコンパイル時 catch されるが、もし無理矢理通せばデッドロックリスク |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03-01 | Tampering | `worker.rs` または `turn.rs` で `use std::sync::Mutex;` を import すると、`.await` 越しの guard 保持で `MutexGuard cannot be held across an await point` コンパイルエラー。回避しようとして `.lock().unwrap()` のような書き換えをするとデッドロックリスク | mitigate | Task 1 と Task 2 の acceptance_criteria で `grep -c 'use std::sync::Mutex' webif/src/{worker,turn}.rs` を `0` 固定。`use tokio::sync::{mpsc, Mutex};` のみ許可。`cargo build --release` でコンパイラが先回り検知 |
| T-02-03-02 | Tampering | `main.rs` で `tokio::spawn(worker_loop(worker.clone(), ...))` の `.clone()` が抜けると、`worker_loop` が `Arc<Mutex<Worker>>` の所有権を奪い、`AppState` 側のフィールドがコンパイルエラーまたは別の `Mutex<Worker>` を作る羽目に。後者の場合 command_handler/restart_handler が worker_loop と別 Worker を操作する silent failure | mitigate | Task 3 の acceptance_criteria で `grep -c 'worker.clone()' webif/src/main.rs` を `1` 固定。`grep -c 'Arc::new(Mutex::new(worker))' webif/src/main.rs` を `1` 固定。`Worker::new` 呼び出しが1回だけであることも `grep -c 'Worker::new' webif/src/main.rs` で確認 |
| T-02-03-03 | Tampering | `Worker::recreate` の `let _ = self.client.close_session(&old).await;`（best-effort cleanup）を `?` で書き換えると、close_session 失敗時に recreate 全体が失敗し、shared-fate 回復が壊れる | mitigate | Task 1 で verbatim 移送ルール厳守。`grep -c 'let _ = self.client.close_session' webif/src/worker.rs` returns `1`（acceptance に明示しないが verbatim 移送で自然に達成） |
